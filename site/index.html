The problem

Everyone has a number nobody can explain.

Making a report has never been easier. Believing one is the hard part, and AI just made the gap wider.

The board deck

“Why does the deck say $4.1M when the dashboard says $3.9M?”

Two hours later someone finds a filter left on in a spreadsheet tab. Nobody wrote down how either number was made.

The AI answer

“Total revenue last quarter was $12.4M, up 8%.”

It reads well and it was instant. But nobody can see what it added up, so nobody can check it, and the next time it might say something else.

The sign-off

“Can you double-check these before Monday?”

Checking means doing the work again, because the work lives in someone’s head, a notebook, or a tool you can’t read.

TraceBi writes down how every number was made, so anyone can check it and nobody has to take it on faith.

Your data, the meaning of each number, and the report itself live as plain files your team can read and review. Every figure on the page is calculated from those definitions and carries its trace, right down to a fingerprint of the result.

How it works

Three steps, from messy data to a report you can check.

Each step is its own stage, so changing a chart never re-runs the slow cleanup, and the meaning of a number never quietly drifts between reports.

Bring your data in

Connect a database or drop in a spreadsheet. A short cleaning step turns it into tidy tables, and checks you choose (no duplicates, nothing missing) must pass, or the run stops.

For engineers
A transform is DuckDB SQL by default (pandas or polars when you need it) that ends by writing star-schema tables to the warehouse. A .contract.yaml beside it declares the checks; a failed check stops the run. A -- source: line reads a table from a database you declared. 
-- transforms/holdings_transform.sql
-- source: crm.issuer_ratings [fallback: inputs/issuer_ratings.csv]

Say what the numbers mean

Write down once what “revenue” or “fair value” means: which column, how it adds up. Every report, and every AI agent, uses that one definition.

For engineers
The model is a short YAML star schema over the warehouse: tables, joins, grain and named measures (ratios, shares, ranks, period-over-period, to-date, percentiles). Classic silent mistakes, such as averaging a ratio or summing a balance over time, are refused with the fix named. 
measures:
  - {name: fair_value, column: fair_value, agg: sum, format: currency0}
  - {name: mark, ratio: [fair_value, cost_basis], format: percent}

Why it matters

Trust you can check, not trust you’re asked for.

Numbers you can follow home

Every figure links back through its query and definition to the tables and files it was built from. Questions that used to take an afternoon take a click.

Agents can’t fake a checked number

Every figure on a TraceBi page is a query against your definitions, recorded in its trace. A number with no query behind it gets no fingerprint, so it can never pass the check.

Reviews that take minutes

A change is a short, readable difference (a definition, a chart’s query) that a person approves, not a spreadsheet to rebuild. Months later, anyone can re-run the check.

AI agents, inside the rules

Let agents do the work. Keep people in charge of the numbers.

Agents read your definitions, answer questions, draft reports and propose changes to the cleanup. They never write to your warehouse themselves: a change to the cleanup runs only after an admin approves it, and each project decides whether a person signs off before a report is published.

A proposed change to the cleanup, step by step:

  1. The agent proposes

    A change to the cleanup step, as a plain SQL file with a note saying why.

  2. A dry run shows the effect

    A proposed cleanup change runs once on a throwaway copy and reports which tables are new, changed or unchanged.

  3. A person approves

    Reviewers read the difference in the app and approve or reject it, with a note.

  4. It’s on the record

    Approval commits exactly those files to git: the agent as author, you as approver.

Print and share

Print it. The trace comes too.

Any report prints to a clean PDF for the board pack. Its last pages are “How these numbers were made”: every figure with its query and fingerprint, the checks the data passed, the build, and the command to re-check it.

  • Send the HTML when people should be able to filter, or the PDF when it’s going in a binder.
  • Schedule it. Refresh the data, build, re-check and email it every Monday, with each run recorded.
  • Keep it honest. The HTML file and its manifest are what the check runs on; the PDF is a print of them.

Single sign-on through your identity provider. Viewers, analysts and admins, and per-project rights to view, build or publish.

Drafts and review

Anyone, person or agent, works in a draft. Publishing into a project asks for approval where the project says so.

Schedules

Refresh, build, re-check and email on a timetable. A failed step stops the run, so nobody gets a stale report that looks fresh.

History

For engineers

Code-first, all the way down.

Three folders, each with its own cadence, handed off at fixed points: the warehouse, then the model. Everything is a plain file in git, reviewed in a pull request, and authored as easily by an agent as by you.

my_workspace/
├─ tracebi.yaml   # the warehouse, the brand
├─ connections/   # databases, one YAML each
├─ inputs/        # raw files
├─ transforms/    # ① SQL (or pandas) → clean tables
├─ models/        # ② tables, joins, measures
├─ reports/       # ③ one project per model
└─ pipelines/     # transform, then rebuild

What a trace proves

  • The query each figure ran, against which definition, and a SHA-256 fingerprint of what came back.
  • Whether that query still returns the same result (tracebi verify: REPRODUCES, SOURCE DRIFT, MODEL CHANGED, MISMATCH…). An undiagnosed mismatch fails loudly.
  • That a built file was not edited afterwards (verify --file, offline).
  • For a SQL cleanup, which source columns each table column is computed from, as DuckDB’s parser reads it.

What it doesn’t claim

  • That a number is correct. It claims the number reproduces; the difference is the product.
  • That the cleanup step’s analysis is right. That code is reviewed in git; its tables are held to the checks they declare.
  • Lineage through free-form pandas or notebooks. The line is drawn where clean tables land.
  • Signed attestation. Manifests are not signed yet, and we say so.
Questions

In plain words.

Do I need to know how to code?
To read reports, ask a model a question or pin a note for an agent: no. To set up the data and definitions, someone writes SQL and a little YAML, or asks an AI agent to draft them for a person to approve. Everything ends up as plain files anyone on the team can read.
Does TraceBi tell me my numbers are right?
No, and on purpose. It tells you where a number came from, which definition it used, and whether asking the same question again gives the same answer. Whether the underlying business data is right is still your call; TraceBi makes it something you can check instead of something you’re told.
Where does my data go?
Nowhere you don’t send it. TraceBi runs on your machine or your servers, reads your databases, and writes reports as single files. There is no telemetry. An AI agent works through TraceBi’s gateway: it can query your definitions, and it reads a source database’s tables only where a person has ticked them.
Which AI tools work with it?
Any agent that speaks MCP, the open standard for connecting AI tools: Claude, ChatGPT, Cursor, VS Code, Claude Code and others. In hosts that show MCP Apps, the report opens live beside the conversation.
Can it read the data we already have?
Yes: Postgres, MySQL, SQLite, Snowflake, BigQuery, DuckDB, CSV and Parquet files. Credentials stay in environment variables or an encrypted store; connection files only name them.
What does it cost?
Nothing. TraceBi is open source under the MIT license. You run it yourself, on infrastructure you already have.
What happens when a number changes?
Re-running the check tells you, and narrows down why: the source data moved, the definition changed, or the cause is unknown, which fails loudly instead of being rounded away.
