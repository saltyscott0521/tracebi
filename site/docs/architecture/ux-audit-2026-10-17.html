UX and UI audit — 2026-10-17

Status: findings and a proposed direction, for decision. Taken from the running product, not the docs: the app was built fresh, the reference project rebuilt, and every page and every report captured at desktop and phone width, light and dark (the contact sheets are in the audit's scratch folder; the captures are reproducible with scripts/ui_audit.py). The quality bar this measures against is the one we set ourselves in Design direction, The UI quality bar and product-strategy.

The short version: the pieces are individually competent and collectively incoherent. The app tells the builder's story (transform → model → reports) to everyone, including the reader whose only job is to open a report. Trust is expressed in five vocabularies. Reports render in four visual languages inside one project. And the one surface that justifies the product, the receipt, looks like a debug log. Each of these is the result of adding a feature as a new page, tab or panel instead of revising the whole.

Part 1 — What the product is, and who is standing in front of it

users-and-jobs names seven users. For the UI, three matter:

Reader Analyst / builder Agent
Wants one report, one number, is it right to make and change reports, see what broke a closed vocabulary and a state it can read
Share of visits most some not a visit — a tool call
What the app shows them today the builder's pipeline the builder's pipeline, plus five ways to look at one report panels inside the reader's pages (notes, feed, Build)

The app has one information architecture, and it is the builder's. That is the root of most of what follows.

Part 2 — Findings: the app

Numbered so they can be referred to. Severity is about the product, not the bug count: S1 breaks the reader's job, S2 confuses or wastes, S3 polish.

Structure

  1. S1 — Reports are not where the app opens, and not in the sidebar. / goes to /models: "Overview · All models · Pick a model", three cards. The sidebar lists Overview, Map, Explore, Drafts, Verify a file. The thing people read is stage ③ of a pipeline diagram on a model's Overview, or an all-models /reports page that no sidebar entry reaches. Sources and History have no entry either; they exist in nav.js PAGES and are reached by the diagram, the palette or a typed URL. There are two navigation systems (the sidebar and PAGES) and neither is complete.

  2. S1 — The primary action on every model page is "Refresh data". It is the big blue button in the header of Overview, Model, Transform and Reports alike, with the subtitle "Rebuild the portfolio warehouse, then its reports." Rebuilding the warehouse is the rarest, most consequential action in the product (admin only, writes to data) and it is presented as the main thing to do on the page where you pick a report to read.

  3. S2 — Five ways to look at one report. The Overview's split preview with its Config tab; the report's own page with Details / Lineage / History / Code panels; Build mode with Changes / Checks / Data; the Drafts preview; and tracebi dev --classic. They overlap (Config and Code both show the package files; Build's Data and Lineage's Queries both list the bindings) and each has its own layout and words.

  4. S2 — Map and the Overview's line draw the same picture. The line is the per-model version, the Map is the all-models version, and each has its own node style, arrows, "Never built" marks and warehouse badge.

  5. S2 — Agent furniture sits on reader pages. The all-models Reports page is "At a glance" followed by "YOUR NOTES — leave your agent a note" and "FROM YOUR AGENT". The Drafts empty state tells a reader to have an agent call start_draft and write_draft_file. These belong to the builder loop in dev mode, not to the library.

  6. S2 — Explore is a form, and the strategy says Ask is path one. Thirteen measures as raw identifiers with checkboxes; a result of one number dressed as "1 ROW · ENGINE: DUCKDB · 54.1 MS", two code tabs and a React Flow diagram with two nodes. No chart, no "keep this", no way from an answer to a draft. It is the builder's query tester wearing the name of the reader's feature.

  7. S2 — Chrome is not role-aware. A viewer sees Rebuild, Edit as a draft, Build, Config and Refresh data; they only learn they may not on click.

Vocabulary

  1. S1 — Trust has five vocabularies. The same fact (this build re-runs to the same numbers) reads "Reproduces" in the list and History, a green "REPRODUCIBLE" badge on every figure in Build mode, "All 6 built reports re-run to the same numbers" under the list, "Re-run check · Reproduces" in Details, and "the sink satisfied its contract" beside it; older builds are "Not checked". The reader has to learn that these are one thing. A trust product cannot afford this.

  2. S2 — Identifiers where names should be. Page titles are portfolio_model in monospace. The library lists portfolio_book while the page inside says "Direct lending: portfolio book". Sources show DUCKDBCONNECTOR as a badge. report.json already carries a name; the model has none. (Backlog item 1 since 2026-10-04, still open.)

  3. S3 — The tagline is "Analytics trust layer". It is category language, not a promise; fine on tracebi.com, odd under the logo of a tool.

State and feedback

  1. S2 — Stale is not visible. The app opened on builds from Oct 9 made from sources changed Oct 17 and the only sign was a "Changed 4:24 PM" in the all-models list. A build older than its source should read amber ("needs a look") everywhere the verdict shows, by the rule we already wrote in Design direction.

  2. S2 — History is a table of dashes. Eight rows of "Report build · succeeded · — · —": no duration, no actor, and the verdict column repeats the same chip. On a phone the row is five columns wide.

  3. S3 — Real console errors on the share link. /r/<name> serves the built file from a null origin and it tries to fetch the selection API, which fails CORS on every load. The file is supposed to be self-contained.

Fit and finish

  1. S3 — Dark mode is two products. The app follows the OS; the report artifact ships light unless look.mode is set, so in a dark app a report preview is a white rectangle, and the share link ignores the OS entirely.

  2. S3 — Phone. The report list truncates descriptions to one line; the floating "Receipt" pill sits on top of chart bars; the model switcher is a chip in the header. Workable, not designed.

Part 3 — Findings: the reports

This is the part the user asked about most directly. The question is not "does it look fine" (it does) but "would a CFO put it in front of the board, and would a design-led company adopt it as their house output." Today: no. Here is why, concretely.

Four visual languages in one project

Look Where Type Ground Hero Shadows / gradients
App dashboard (app.jsx) dashboard, overview, desk, concentration, mrr Hanken Grotesk white cards on #f6f6f7 none hairline
Editorial (.tb-article) book, cohort_brief serif headline, text in Hanken sheet on grey, hatched hero band slate (book) / electric blue (brief) sheet shadow
Showcase portfolio_showcase Fraunces display + Inter white navy→teal gradient drop shadows, pill tabs
Bespoke affordability, aum_by_branch own fonts and palette own own own

Plus a fifth in the codebase: the legacy HTMLRenderer (theme.py DEFAULT_CSS: Segoe UI, 13px) still renders the spec path and the Excel companion. The design direction says one blue, no gradients, no resting shadows; the showcase, the kitchen-sink demo agents are told to learn from, breaks all three. The one report people consistently call good, affordability, is good because a person designed it by hand. The framework's defaults do not produce that page; that is the gap to close.

What specifically reads as "not premium" in the default dashboard

Taken from portfolio_dashboard and portfolio_overview, the pages a new project gets.

  • No masthead. A title, a sentence, and "Built Oct 17, 2026, 4:32 PM" floated right. No place for the organisation, the period the numbers cover, the status of the build, or a mark. A premium report is framed; this is a page that starts.
  • The KPI strip has no hierarchy. The lead cell is twice as wide and mostly empty; "Positions 25" is set at the same weight as "$285.9M". The context line ("administrator marks") is a caption, not a signal — no delta, no direction, no colour meaning. The eye lands on the chart, not the number.
  • Two blues. Bars are --tb-chart-1 #2a78d6; the accent, links and the app are #2f5bea. Close enough to look like a mistake.
  • Charts are the library default. Full-saturation bars at 70% of the row height, square ends, full gridlines, no value labels, truncated category labels ("Cedar Credit Partn…"), and axis ticks that collide in a narrow card ("$0 $20M$40M$60M$80M$100M$120M" on By fund). The tooltip is a white box with a swatch.
  • Data bars in tables are a lavender highlight behind the number. They read as a selection artefact or a rendering glitch, not as a bar.
  • A methodology dump on every page. "About this report" plus the transform's statement plus every measure definition, in 9px grey, under a 150px void. It is honest, and it is the first thing a reader scrolls to and the last thing they want on the page. It belongs in the receipt.
  • The receipt drawer is a log. rendered 2026-10-17T16:32:54.924338+00:00, git d965fafc…, then "Fair value · $285.9M / Fair value / ▶ Details" seven times. This is the feature. It should look like a certificate: the verdict first, then each figure with its value, its definition in plain words, its query in one line and an abbreviated fingerprint, with the raw detail behind a disclosure.
  • Layout gaps. The overview's content ends at 60% of the viewport and the About block floats below; portfolio_desk's sidebar stops at the fold and the About block runs full-width under it. A page should end on purpose.
  • Light only, by default. See finding 14.

What the editorial gets right, and where it falls short

The hero band, the serif headline that states the finding, the standfirst and the pull-stat are the right instincts: a report that reads. But the hero colour is derived per report (color-mix on the accent), so one project's editorials come out slate, electric blue and green; the hatched texture is decoration; the KPI strip is the dashboard's, dropped in without adaptation; and the same methodology dump closes the page.

Part 4 — Diagnosis

Three structural causes, not fifteen bugs.

  1. The IA is the engineering pipeline, not the user's job. "Transform → Model → Reports" is how a number is made. It is the right spine for the docs and the CLI. It is the wrong front door for a person who wants a report, and it forces every page to carry the whole pipeline.

  2. Features were added as surfaces. Map, Drafts, Verify, the Lineage panel, Build mode, Config, Desk, the agent feed: each landed as a new page, tab or panel with its own layout and words, because that is the smallest change that ships a feature. None of them revised what was already there. The result is a product with more places than ideas.

  3. The report design system is a stylesheet, not a system. tracebi.css is 1,300 lines of good rules with no type scale, no masthead, no chart style beyond colours, and three independent "looks" layered on top (12b, 12c, 12c-2) plus six themes and a legacy renderer. Every report pass, including the last three commits, styled reports one at a time instead of fixing the defaults they inherit — which is exactly the volume trap the derive-defaults note warns about.

Part 5 — Proposed direction

5.1 One IA, built on the three paths

Four top-level places. Everything else is inside one of them.

Place For Holds Replaces
Reports (home) reader the library: folders by model, search, status chips, open a report /, /reports, Overview stage ③, Map's report column
Ask reader, analyst a question → an answer with a small chart or table, the definition used, "Keep this" → draft; the query builder behind "advanced" Explore
Data builder one page per model: the line as its header, then tabs Model · Transform · Sources · Runs Overview, Model, Transform, Sources, History, Map
Review approver, builder drafts, publish requests, run history with failures first, verify a file Drafts, Verify, History

Rules that go with it:

  • A report page is the report. Full width, the artifact as the reader will receive it, one quiet trust chip in the header, and one side panel ("About this build": verdict, lineage, history, files) instead of four. Build mode stays, dev-mode only, as the one builder overlay. Config merges into the panel's Files.
  • Role-aware chrome. A viewer never sees Rebuild, Edit, Build or Refresh. The role is already known (/api/me); use it.
  • Agent surfaces live in dev mode. Notes and the agent feed appear in Build mode and in tracebi dev, never on the library.
  • Names everywhere, identifiers in Code. report.json name is the display name; models get a label; identifiers appear in monospace only in the Code tab and the receipt's query lines.
  • One trust vocabulary, one component. A Verdict chip with four states (Reproduces · Needs a look · Does not reproduce · Not checked), the same colour rule as Design direction, used in the library row, the report header, the receipt, History and Review. "Source changed since this build" is Needs a look, everywhere at once. Figure badges in Build mode use the same chip.

5.2 A report design system worth the name

Define "premium" as a checklist, then make the defaults meet it, so that a page with no style.css is the page we would show. Concretely:

Type. One display face for headlines and the lead number, one text face, one mono; a seven-step scale; tabular numerals on every figure; negative tracking above 32px. The editorial and the dashboard share the scale and differ in which steps they use.

Frame. A masthead on every page: a mark slot (the org's, or ours), the report's name, the period the numbers cover, built time, and the verdict chip. A measure of 1,200px with a 12-column grid. A footer that ends the page: sources and "How these numbers were made" collapsed, one line visible. The methodology dump moves into the receipt.

Numbers. A KPI is a number with a signal: the lead at 3.2em, a delta with direction and semantic colour where the model gives one, context in one short line, an optional spark. No empty 2× cell: the lead is bigger, not wider.

Charts. One chart style, not a library default: the series colour is the accent family; bars at 55% band with 2px radius; direct value labels on bars and end-points; category labels wrapped or placed inside, never truncated; gridlines at 6% ink; axis formats from the same formatter as the tables; a tooltip that names the value, the definition, and links the receipt. Six chart types, each with a reference rendering in the showcase.

Tables. Right-aligned numbers, a sticky header, a thin data bar in its own cell (not a highlight behind text), one totals style, row density from the page's density token.

Receipt. Redesigned as the product's signature: the verdict first, then figures as a list of "value — definition — query — fingerprint", the raw manifest behind a disclosure. The same panel in the artifact and in the app's report page, so a reader learns it once.

Modes. auto by default: the artifact follows the OS as the app does. Dark is designed, not derived.

One system, two registers. Dashboard and editorial are the same tokens, masthead, KPI, chart and table styles in two layouts. The hero band keeps one accent (not a derived colour per report) and loses the hatch. Themes become accent presets on one system; the six files collapse into tokens. The legacy DEFAULT_CSS renderer either takes tracebi.css or is retired from the HTML path (Excel keeps its own).

The showcase is rewritten to the system. It is what agents are told to copy; today it contradicts the design direction. After the rewrite it should be the proof that the defaults are enough.

5.3 How we keep it that way

  • A report contact sheet in the audit loop. scripts/ui_audit.py already crawls the app; it should also render every report in both modes and both widths into one sheet, and the loop in The UI quality bar reviews it by eye before each release. Numbers to track: distinct font families, distinct accent hues, and "looks" per project (target: one).
  • New-surface rule. A feature that needs a new page, tab or panel first says which of the four places it lives in and what it replaces. "Another panel" is not an answer.
  • Default-first rule for reports. A visual change lands in the system (tracebi.css, the kit, the scaffold) before, or instead of, a report's own style.css. The reference project's style.css files should shrink with every pass, not grow.

Part 6 — Sequence

Ordered by what the reader sees first, and so that each step is shippable.

  1. Report design system v2 (the artifact is the product): tokens, type scale, masthead, KPI, chart style, tables, footer, receipt, auto mode; dashboard and editorial on one system; showcase rewritten; scaffold and _INIT_SAMPLE_APP_JSX updated; design-direction revised to match. The discoverability definition of done applies: vocabulary, scaffold, guides.
  2. Reports as home + the report page: library view, verdict chip everywhere, names not identifiers, role-aware chrome, one side panel, the methodology moves into the receipt, the share-link fetch bug.
  3. Collapse the builder pages into Data and Review: the line as the model header, tabs, Map and Verify folded in, agent surfaces to dev mode.
  4. Ask: answer with a chart, the definition in words, "Keep this".

Step 1 is the one to start on. It fixes what the user named, it touches no information architecture, and every later step inherits it.
