What is TraceBi?

TraceBi is a code-first BI framework organised around a three-phase workflow that carries data from messy to reportable: manipulate it with unconstrained pandas and sink clean tables to a warehouse; declare a thin model over that warehouse; point a dashboard at the model. Each phase is a project-root folder with its own cadence, and the phases are decoupled by freeze points — a materialized artifact handed from one to the next — so the slow analysis and the fast reporting never block each other.

From the model boundary onward it is also a trust layer. Once the numbers are frozen into the warehouse they become a contract you can report against: models, facts, dimensions, named measures. Every figure a dashboard shows is a live query that comes back stamped — the resolved query, the lineage chain, and a SHA-256 fingerprint of the complete result — and tracebi verify can re-run any manifest to prove it still reproduces. This machinery covers phases 2 and 3. It deliberately does not reach through the raw phase-1 analysis; the line is drawn at the sink (see the verify loop).

Underneath is the kernel the whole workflow rests on. A DataSet is an immutable pandas wrapper that records every operation in a lineage chain; a DataModel is the star-schema contract (tables, relationships, facts, dimensions, measures); the report engine renders declarative specs to self-contained HTML with a lineage manifest beside every artifact (Excel remains a Python-framework renderer; spec and dashboard renders are HTML today).

The three-phase workflow

Manipulate → freeze → model → freeze → dashboard. The reference implementation ships in the repo; python run_workflow.py runs it end to end.

①

Manipulate

transforms/

Ordinary, unconstrained pandas. Pull the queries you need and do the real analysis — window functions, prose parsing, cleaning, dedupe — then write ("sink") clean star-schema tables into a file-backed DuckDB warehouse. The framework does not constrain how you clean; the contract is what lands: the named tables at the end of the script.

Model

models/

A declarative DataModel (star schema) over the warehouse: grain, keys, measures, in a few dozen lines a reviewer reads without opening the pandas above it. It reads the sink; it never sees the transform.

❄ freeze the model — the semantic contract
③

Dashboard

dashboards/

A ReportSpec (JSON) pointed at the model — KPI cards, charts, tables — where every figure is a live query. Because the model is materialized, the page re-renders in milliseconds with no pandas in the loop. Served on the Reports page of the web UI.

dashboards/portfolio_dashboard.json

Why the split: the slow, unconstrained analysis (①) and the fast, iterated reporting (③) never block each other, because the model (②) is a frozen contract between them. Editing the dashboard never re-runs the pandas. To add a panel, add a section to the JSON with a data.query naming a fact, its measures and dimensions — no code, no re-run of phase ①. A metrics section can carry a query too: a KPI card whose value names a measure reads it live from a one-row result, so the strip never goes stale.

The two planes

Change the contract in git. Use the contract over MCP.

PlaneWhat lives hereSide effects
Definition (git) models/*.py, pipelines/*.py, reports/*. A missing measure is fixed by a code-reviewed edit to the model file — never a workaround in the report layer. Code review is the write gate.
Access (MCP / web / CLI) Queries, validation, spec rendering, verification. Read-and-compute only; nothing persists beyond an output file. Pipeline execution writes to the warehouse and is deliberately absent from the agent surface.

The assurance ladder

Assurance is graded, not binary — each level up is more the company can prove about a number.

LevelAgent doesCompany can prove
L0Raw SQL, raw HTMLNothing. Avoid.
L1Queries via the gateway, renders its own HTML, cites a fingerprint per numberEvery number traceable to a stamped query
L2Emits a ReportSpec; TraceBi validates and rendersArtifact reproducible from its manifest
L3L2 + signed manifest + re-verificationAttestable. Re-verification exists today (tracebi verify); signing is not yet built

Prefer L2. Use L1 when you need presentation freedom the spec grammar lacks — governed data, ungoverned presentation. Rows are transport; the stamp is the truth: query_model caps returned rows but fingerprints the uncapped result, so a figure beyond the cap is still verifiable.

The verify loop

Where the trust story starts and stops. Stamped queries, spec validation, and tracebi verify apply from the model boundary onward — phases 2 and 3. Tracing lineage through the raw phase-1 analysis is intentionally not done: the framework draws the line at the sink, where the numbers become a contract you can report against. tracebi verify re-runs a manifest's recorded queries and compares fingerprints. It does not read a transform, and it does not assert a number is correct.

Every render records each source table's input fingerprint in the manifest. tracebi verify <manifest> — or the gateway's verify_manifest tool — re-runs every recorded query and classifies each section:

VerdictMeaning
reproducesSame inputs, same fingerprint. The receipt holds.
source_driftThe inputs moved; the result changed with them.
model_changedA table now loads from a different source or connector — a governance event, never counted as benign drift.
unexplainedInputs match but the result doesn't. The alarm.
unverifiableNo recorded query, or post-query transforms.
 
$ tracebi verify output/report.manifest.json
# exit 0 = all reproduce (or all honestly unverifiable) · 2 = drift
# exit 1 = alarm, or nothing to check at all

The receipt as a whole gets one verdict, and reproduces is the only one meaning a number was re-run and matched. A manifest with no data-bearing section verifies nothing, so it is a broken receipt, not a passing one (nothing_to_verify, exit 1); a manifest whose every section is hand-transformed is unverifiable — still exit 0, but it says so rather than borrowing the passing answer.

The canonical agent loop ends with this step: discover → explore → author → validate → render → verify → cite. Anything but reproduces needs explaining before a human sees the number.
